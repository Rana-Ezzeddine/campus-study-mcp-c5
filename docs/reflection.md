# Reflection

I drew the boundary between the tools according to their observable effects. `search_rooms` only reads the fictional catalog and reservation state. `reserve_room` commits one reservation and checks the conditions required for that write to be valid. `find_and_reserve` expresses the higher-level goal of obtaining a suitable room by calling the same search and reservation capabilities. It does not duplicate their filtering or persistence logic. The orchestration is deterministic: it tries the smallest matching room first, then another matching room if a competing request took the first one. Internal function calls are intentional; making the server connect back to itself through MCP would add transport overhead without improving this workflow.

Three tools are sufficient for this narrow use case because they separate inspection, one state change, and one coordinated goal. The important challenge is preserving that separation while handling retries and concurrency. An availability result is not a guarantee, so the action rechecks constraints and uses a transactional unique slot constraint. Both write-capable tools use request IDs, preventing an identical retry from creating another booking. A production version would need authenticated student identities, a real campus availability source, cancellation, booking limits, and access controls. Those additions would justify more tools; they are intentionally outside this assignment. The first real integration run exposed an MCP version mismatch in test field names; correcting those names and pinning the resolved versions made the checks pass on Python 3.11 and 3.13. The validation record distinguishes these real transport and SDK Runner checks from live-model routing, which still requires an API key.
